# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`dsh-hot-reload` is a DeepSeek Harness (dsh) plugin, published to npm, that live-reloads *upgraded* plugin packages without restarting dsh. dsh's built-in `cordis-plugin-hmr` deliberately ignores `node_modules`; this plugin closes that gap. The reload engine lives in `lib/index.js` (ESM, Node >= 22, only dependency is `chokidar`); `lib/client.js` is an optional browser half that draws the notification banner (see "Notifications").

There are no tests, no linter, and no build step in the repo — the published `lib/` is the source. dsh's own source is checked out at `/home/stuart/deepseek-harness` and is the authority for any dsh internal this plugin touches — read it rather than the built bundles under `~/.npm/_npx`. Verify against a real dsh profile (built/tested against dsh `0.1.0-rc.6`), or drive `apply()` with a fake ctx/loader: the plugin only needs `ctx.loader.entries()`, `loader.internal`, `loader.import`, `loader.unwrapExports`, `ctx.registry.delete`, `ctx.effect`, `ctx.inject`, and `ctx.baseUrl` (omit that last one and `resolveProfileDir` returns null and `apply()` bails early — unless you pass `config.profileDir`, which always wins). `ctx.logger` is optional; it falls back to `console`. To reach the notice channel, the context your stub `ctx.inject` calls back with needs `webServer.register` and its own `effect`. A temp profile dir plus those stubs exercises the whole cycle without dsh. Note chokidar needs ~300ms to establish the watch before the first lockfile write registers.

`lib/client.js` is testable without a browser: stub `window.__ModuleLoader__` to capture the `factory`, call it with a `require` returning `react` plus a fake primitives object, and drive the returned `apply`. Passing a react stand-in whose `useState`/`useEffect`/`useCallback` you control lets you feed frames through the captured SSE listener and assert the rendered `Toast` props directly — no DOM needed. To exercise the reconnect, also stub `globalThis.EventSource` (a class recording each instance, with a `fire(type, ev)` helper and a settable `readyState`) and `setTimeout`/`clearTimeout` with a virtual clock — otherwise walking the full `RETRY_DELAYS_MS` schedule takes three real minutes. `readyState` is what selects the path: 2 is the fatal one that re-arms, anything else must be left alone.

## How it works (lib/index.js)

- **Detection**: watches the profile's `pnpm-lock.yaml` with chokidar (debounced, default 300ms). On change, `runCycle` builds one `snapshot()` — a single `loader.entries()` enumeration plus one `package.json` read per package — and diffs its versions against the tracked map. The lockfile is only the *trigger*; versions come from `node_modules/<pkg>/package.json`, which is the only source that describes what an import would actually get.

  On write ordering: measured against pnpm 11.21.0 (`add`, `update`, and `install`, four runs), pnpm writes `node_modules` **first** and the lockfile **last**, 20–40ms after the last package is materialized — so a cycle triggered by the lockfile always sees settled versions. (Both this file and the comment in `lib/index.js` once claimed the reverse order; that was wrong for pnpm 11 and is corrected in both places. If you find the old claim anywhere, it is stale, not a second measurement.) The design does not *depend* on either ordering being safe, but be aware of the exposure: if some pnpm version ever wrote the lockfile first, a cycle would read stale versions, `continue` past them, and never re-arm (nothing else is watched), silently missing the upgrade forever. The 300ms debounce is no defense — the materialization window measured 2.5–4 seconds. A settle/confirm pass would close this; it is not implemented, and the README states the exposure under "Limitations" so users are not left to discover it.
- **Reload** (`reloadEntry`): resolves the module URL via `loader.internal`, invalidates the package's cached modules — the entry plus every cached module under the package's own directory (found by walking up to the nearest `package.json`), in both the ESM `loadCache` and the CJS `require.cache` — re-imports, then swaps every fiber of the module's runtime in place (`registry.delete` old plugin, `reattach` new plugin to each old fiber's entry + config). The directory scope is what makes multi-file plugins reload as one unit under a hoisted linker, where a version bump rewrites files in place at the same URLs; shared dependencies live outside the package directory and are left alone. Mirrors the technique of `cordis-plugin-hmr`.
- **Rollback**: the reload is optimistic. `fiber.await()` surfaces sync *and async* `apply()` startup errors into the try/catch; on failure the old plugin is re-instantiated, so a failed reload never leaves a dead plugin — just a logged "restart dsh" notice.
- **Fail-safe degradation** is a design invariant: missing `loader.internal`, unresolvable profile dir, opt-out (`dsh.hotReload: false` in the target plugin's package.json) — all degrade to logging "restart needed", never to crashing dsh.

- **Notifications**: `report(kind, message)` is the single outcome seam. From one message it writes the `ctx.logger` line (level chosen by `kind`), a stderr line when `kind` is `"reloaded"`, and an SSE frame to `GET /dsh-hot-reload/events` for every kind. `lib/client.js` subscribes to that channel and renders the shipped `Toast` into the `shell.overlay` slot. stderr exists because dsh's host registers no cordis logger exporter, so nothing logged reaches the terminal. Fire and forget: nothing buffered, no cursor, no dismiss path.

Invariants worth preserving when editing:

- **Notifications are additive and must never throw into a cycle — or into `apply()`.** `report()` swallows socket and stderr errors, the route registration catches its own failure and returns a no-op disposer, and the client half no-ops if a seed module, `Toast`, or the slot is gone. The `ctx.inject` block itself is wrapped and deliberately registered **last**, after the watcher and its disposer: registered earlier, any throw from it would abort `apply()` before the watcher exists, so a cordis API this plugin uses only for *notices* would cost the *reloading* — and dsh's boot sweep (`assertEntriesActivated`) turns a FAILED entry into a refusal to start at all. Keep it last and keep it guarded. A broken notification must never turn a working reload into a failed one.
- **`HEAD` on the events route is answered and closed, never streamed.** Node discards a `HEAD` response body, so handing one the normal stream blocks the caller until its own timeout while its socket sits in `connections` collecting writes nobody reads — a hang plus a leak, reachable from any health check or link prefetcher. (dsh's own `client-hmr` channel has the same shape and the same bug; don't copy it back.)
- **One message per outcome, authored once.** Call `report()` for cycle outcomes and `log.*` directly for diagnostics. Never hand-write a log string and a near-identical notice string at the same site: this is the code path whose whole job is reporting honestly, and two copies drift silently until the terminal and the banner disagree.
- **`ctx.inject(["webServer"], …)` — never a module-level `inject`, never `ctx.get`.** A module-level `export const inject` is *required* (`Inject.resolve` maps every name to a wait), so it would park the whole plugin forever in a profile that has none — `tui` would stop reloading anything at all. `ctx.inject` parks only a child fiber. `ctx.get` is wrong for a different reason: it resolves strictly (`undefined` unless the providing fiber is already ACTIVE) while `WebServer` activates only after its async `listen()` binds and loader entries start concurrently — so it both races and, being one-shot, never recovers when the web server is replaced.
- **`lib/client.js` is hand-written in the browser loader's bundle format** (`window.__ModuleLoader__.load({id, factory})`) precisely so the package keeps having no build step. That means: no JSX (`React.createElement`), no import/export syntax, and only the *platform seed* modules may be `require`d. The seed table is the authority (dsh's `packages/client/web/src/seed.ts`) and its keys are exact — note the scope, which is easy to drop by mistake: `react`, `react/jsx-runtime`, `react-dom`, `react-dom/client`, `@deepseek-ai/cordis`, `@deepseek-ai/dsh-client-ui-slots`, `@deepseek-ai/dsh-client-web-react`, `@deepseek-ai/dsh-client-ui-primitives`, `@deepseek-ai/dsh-client-ui-attachment`, `@deepseek-ai/dsh-client-schema-form`. Requiring anything else resolves against another plugin's bundle or throws. `id` must stay the package name.
- **A require miss in the client half costs the whole page, not just the banner** — which is why the requires sit in a try/catch that degrades to a no-op plugin. The web shell's boot sweep (`assertEntriesActive`) throws a boot failure for *any* loader entry that did not reach ACTIVE, so a factory that throws (no fiber) or an entry left PENDING on a service that never arrives takes down the app, not just this contribution. The guards in `apply()` are what keep "you lose the banner, never the page" true; keep them.
- **`EVENTS_ENDPOINT` is duplicated** in both halves on purpose — they are separate bundles (Node ESM and a browser classic script) with no module in common and no build step to generate one. Change one, change the other.
- **Mount into `shell.overlay`, never `root`.** `root` is a single-occupancy slot already held by dsh's app frame; a second registration there shadows the entire UI rather than sitting beside it. `shell.overlay` is a root-scoped *list* slot that stays mounted with no conversation open — which a reload notice needs, since reloads are triggered from a terminal.
- **The client must re-arm its own `EventSource`, on a bounded budget.** A CLOSED `readyState` is fatal — the browser will not retry it — and it is reached routinely, not rarely: with no route registered the request falls through to dsh's SPA fallback and gets `200 text/html`, which happens on every dsh restart because `WebServer` binds its socket before this plugin's route is added. Without re-arming, one ill-timed retry costs the banner for the life of the tab. The budget is the `RETRY_DELAYS_MS` **array length**, so a profile with no host half stops knocking; a successful `open` resets it, which makes the bound per outage while still bounding "nothing is ever there". A CONNECTING `readyState` is not fatal — leave those to `EventSource` itself.
- **A retryable outcome must not re-announce itself every cycle.** The "no live fiber" path returns `false` on purpose, so the version stays uncommitted and *every* later lockfile write — including ones for unrelated packages — re-detects it. As a log line that was noise; as an undismissable banner it followed the user through routine `pnpm add` work. `noticedVersions` gates the announcement per package+version (cleared on commit and on drop, alongside `failedVersions`). Gate the *announcing* only — never the retry. Any future retryable `report()` site needs the same gate.
- **`Toast`'s `onDone` must keep a stable identity** (`useCallback` with no deps). Toast restarts its hold-and-fade timer whenever `onDone` changes, so a fresh arrow per render lets a burst of arrivals keep resetting the banner already on screen instead of letting it finish and hand over.

- Reload cycles are **serialized** (the `running` promise chain) — never let two cycles run concurrently against the registry.
- **`snapshot()` is the only place that classifies rows.** It answers every "what kind of row is this" question once per cycle: group rows and disabled rows are excluded, `live` holds one entry per **runtime** (rows/aliases sharing a runtime double-apply if reloaded separately, while one specifier under two loader trees is two runtimes and both must reload), and `fiberless` counts enabled-but-unattached rows. `handlePackage` filters nothing — keep it that way rather than re-introducing a second classification site.
- **One snapshot per cycle, consumed by everything.** Never re-enumerate entries or re-read a `package.json` outside `snapshot()` — a mid-cycle loader/fs hiccup would make a real upgrade look like "not a loaded plugin" and get committed as loaded, losing it silently. The single deliberate exception is the at-import version read below.
- The committed version is **captured at import time inside `reloadEntry`**, never re-read after the reload. Re-reading can record a version that was never imported (one that landed during a slow `apply()`), which makes the next cycle see no change and skip that upgrade forever. If a package's modules import *different* versions, commit nothing and return retryable `false` — the next cycle re-snapshots and converges, which is why no version-comparison helper is needed.
- **Terminal vs retryable failure** is a real distinction: `handlePackage` returns `TERMINAL` only when a reload was *attempted and failed* (recorded in `failedVersions`, never retried — each retry tears down the working rolled-back plugin), and plain `false` when it couldn't attempt at all (teardown, or no fiber attached yet), which stays retryable.
- **Never fake success, never cry wolf.** A changed package whose enabled rows have no live fiber warns and doesn't commit; a *disabled* row is skipped silently (it isn't running, and re-enabling loads fresh code). Use the inherited `entry.disabled` getter — never `options.disabled`, which can be a `!!js` expression object and misses ancestor-inherited disabling.
- An **explicit `config.profileDir` always wins** over auto-detection, even without a lockfile (warn, don't override).
- **Tracking follows loader membership, not the filesystem**: drop a package when no loader entry is backed by it. Directory probes are wrong twice over — a dangling pnpm symlink mid-swap would evict a live plugin, and a removed plugin row whose package stays installed would be tracked forever. A degraded `snapshot()` (loader throwing) returns null and the cycle does nothing; a boot-time degraded snapshot means the first successful snapshot is simply adopted (deliberate: a first-event upgrade in that rare window is absorbed silently).
- A package whose `package.json` can't be read is tracked with a **null version**, not omitted. Omitting it makes its first readable version look like a brand-new row that gets adopted without a reload — stale code, no warning. (Presence is tested with `in` and equality against a non-empty string, so `null` needs no sentinel value.)
- **Shutdown never waits on a reload.** The disposer sets `disposed`, closes the watcher, and returns. Because nothing waits, `reloadEntry` must check `disposed` on *both* paths after activation: the failure path skips the rollback, and the success path deletes the freshly activated plugin — otherwise its timers and sockets outlive shutdown with nothing left to dispose them.
- The reload path uses cordis/loader internals (`loader.internal.loadCache`, `resolve`/`resolveSync` per `internal.version`, `registry.plugin`/`delete`, `fiber.entry`) — the same ones HMR uses. Changes there in future cordis versions must fail closed to "restart needed".

`cordis.patch.yml` is the bundle patch dsh applies at boot to mount the plugin (referenced from `package.json`'s `dsh.bundle.patch`). Only two config keys exist — `debounce` and `profileDir` — and its commented example must stay in sync with them.

## Releasing

Publishing is fully automatic via npm Trusted Publishing (OIDC, no NPM_TOKEN). `.github/workflows/publish.yml` is triggered **only by pushing a `v*` tag** — pushes to `main` do not publish. The run fails loudly if the tag disagrees with `package.json`'s version, if the version is a prerelease (**stable releases only** — this project never publishes RCs), or if the registry check fails for any reason other than a confirmed E404; an already-published version is skipped. Nothing runs after `npm publish` — if two releases are ever cut minutes apart and publish concurrently, `latest` can land on the lower version; fix that by hand with `npm dist-tag add`.

To cut a release: bump `version` in `package.json`, add a `CHANGELOG.md` entry, commit, push, then push the matching `v<version>` tag. Keep `README.md` and `README-zh.md` in sync — both ship in the package.
